# План реализации: Улучшения VSA Trading Assistant

## Описание задачи
Этот план направлен на исправление критических архитектурных и логических проблем, выявленных в `Critics.md`, с учетом ваших дополнительных правок из `Plan.md`. Главная цель — использовать правильные данные для VSA (фьючерсные котировки с сохранением спот-базиса), повысить надежность анализа бота, внедрить строгую валидацию сигналов и правильное логирование в SQLite для всех режимов работы.

## Согласованные детали
- **Источники данных:** OHLC и Volume берутся из фьючерса (`6E=F`). При этом мы параллельно продолжаем получать спот, но исключительно для расчета базиса (сдвига) по 20 последним свечам. 
- **История чата:** Храним ~10-12 сообщений, но с общим лимитом ~20 000 символов, обрезая старые. Полный JSON свечей — только в последнем запросе.
- **Температура:** 0.2. Если API выдает ошибку 400 из-за параметра температуры (актуально для reasoning-моделей), делаем повторный запрос без него.

## Предлагаемые изменения (разбиты на этапы)

---

### Этап 1: Данные и Тесты (Подготовка фундамента)
*Цель: Исправить данные для VSA (фьючерс), рассчитать правильные признаки, разобраться с базисом. Внедрить постоянные тесты вместо временных скриптов.*

- **Исправление `get_market_data` (`core.py`)**:
  - Запрашивать около 85 свечей для обеих серий (фьючерс и спот).
  - Рассчитывать `basis = median(fut_close - spot_close)`.
  - Рассчитывать признаки VSA только по фьючерсу: `rel_volume` (Volume / SMA20), `spread` (High - Low), `close_pos` (относительное положение).
  - Определять торговые сессии (Asia, London, NY, overlap) и наличие разрывов в котировках (CME пауза 17:00-18:00 ET).
  - Отбрасывать текущую (незакрытую) свечу, оценивать возраст последней закрытой свечи и возвращать флаг устаревания (`is_stale`), если свеча старше 20 минут.
  - После расчетов делать срез до 60 свечей (`tail(60)`), чтобы избежать NaN-значений в `rel_volume`. Возвращать JSON с `allow_nan=False` для защиты.
- **Постоянные тесты**: Создать директорию `tests/` с файлом `test_core.py` (под `pytest`). Зафиксировать фикстуры (pickle) для `get_market_data`, чтобы тесты не зависели от сети.

---

### Этап 2: Промпт, Парсинг и Валидация
*Цель: Обеспечить стабильное извлечение сигнала из ответа LLM и предотвратить выдачу опасных ордеров.*

- **Обновление промпта (`core.py`)**:
  - Явно указать инструмент: «Твой торговый инструмент: фьючерс EUR/USD (CME 6E), цены фьючерсные, тик 0.00005».
  - Заменить жесткие цены `1.0850` в примере JSON на плейсхолдеры (`<entry>`, `<stop>`) во избежание галлюцинаций LLM.
  - Изменить порядок блоков `get_system_prompt_blocks` для эффективного кэширования: сначала статический референс книг, затем инструкции.
- **Структурированный вывод и парсинг**: В `extract_signal` сначала пытаться использовать `response_format: json_schema` (через настройки `call_llm`, если поддерживается). Затем fallback на регулярное выражение ` ```json `, затем fallback на поиск последнего `{...}`.
- **Строгая валидация и базис (`core.py`)**:
  - В `calculate_position_size` внедрить проверки: `abs(entry - last_close) < N` (отсечение оторванных от рынка уровней) и `stop_distance >= max(5 пипсов, 0.5 * ATR14)`.
  - Возвращать текстом причину отказа (например: "Сигнал отклонён: стоп 0.8 пипса < минимума 5"), чтобы пользователь понимал, почему нет расчета.
  - Конвертировать фьючерсные уровни обратно в спотовые (`spot_level = fut_level - basis`) и показывать обе цены в блоке расчета позиции. Объем считать под стандартный спот-лот 100 000.

---

### Этап 3: Надежность, Журналирование и Реплей
*Цель: Сохранять каждый анализ в БД (и для бота, и для веб-интерфейса), улучшить обработку ошибок, добавить инструменты бэктеста.*

- **SQLite Логирование в ядре (`core.py`)**: Внедрить запись сигналов, ответов LLM и токенов в `signals.sqlite` прямо внутри пути `call_llm` -> `format_response`. Это гарантирует логирование и консольного бота, и Streamlit интерфейса.
- **Улучшение `call_llm`**: Возвращать кортеж `(ok: bool, text: str, usage: dict)`. Обрабатывать HTTP 429 с учетом `Retry-After`.
- **Планировщик `bot.py`**: Заменить `print` на модуль `logging`. Рассчитывать точное время сна до следующего слота `time.sleep()`, чтобы избежать двойных запусков и дрейфа времени.
- **Режим реплея**: Добавить скрипт (или функцию) для прогона исторических свечей через пайплайн `format_response`, чтобы быстро собирать статистику сигналов без ожидания реального времени.

---

### Этап 4: Пользовательский интерфейс и Окружение
*Цель: Очистить чат от огромных JSON, улучшить отображение статусов и навести порядок в репозитории.*

- **Оптимизация UI (`app.py`)**: 
  - Обрезать историю сообщений (до ~12 сообщений / 20 000 символов), передавать полный JSON только в последнем запросе. 
  - Выводить количество использованных токенов (`usage`) и текущий базис.
  - Грамотно отображать причины отклонения сигналов и ошибки API (чтобы они не попадали в историю как ответы ассистента).
  - Использовать флаг `is_stale` от `core.py` для отображения предупреждения о закрытом рынке (вместо локального `weekday()`).
- **Окружение**:
  - Зафиксировать зависимости в `requirements.txt` (например, `pandas==3.0.5`, `yfinance==1.5.2`).
  - Убрать `pymupdf4llm` из основных зависимостей и перенести `pdf_to_md.py` в папку `tools/`.
  - Добавить `.gitignore` (добавить туда исходники книг-источников, .env, .venv, *.pdf, db). 
  - После настройки `.gitignore` выполнить `git init`.

## План проверки
После Этапа 1 (Данные) мы сделаем 5-10 ручных тестовых прогонов (через скрипт или UI), чтобы визуально оценить формируемый JSON (правильность базиса, признаков VSA) **до** того, как LLM начнет на них обучаться.
В дальнейшем стабильность функций ядра будет поддерживаться через `pytest`.
